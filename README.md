# Databricks Telematics Pipeline

This project implements a small streaming data pipeline in Databricks for processing truck GPS data.

The pipeline generates synthetic GPS pings for a fleet of trucks, ingests the files using Auto Loader, cleans and deduplicates the data, and joins it with static truck information to create a current-position dataset.

The solution uses a Bronze → Silver → Gold architecture and is deployed using a single Databricks Asset Bundle across dev, test, and prod.

## Architecture

```text
GPS Ping Generator
        |
        v
Unity Catalog Volume
(JSON files)
        |
        v
Auto Loader
        |
        v
Bronze
(raw GPS events)
        |
        v
Silver
(validated + deduplicated)
        |
        |       truck_details
        |       (static table)
        |             |
        +-------------+
              |
              v
Gold
(current truck position
 + truck/driver details)
```

## How the Pipeline Works

### Bronze

The GPS generator writes JSON files to a Unity Catalog Volume.

Bronze uses Databricks Auto Loader to incrementally discover and process new files. The data is written to the `bronze_pings` Delta table.

I intentionally keep Bronze close to the source data. This means duplicate records and bad coordinates are still stored in Bronze so the original data is available for troubleshooting if needed.

I also add the ingestion timestamp and source file for basic lineage.

Auto Loader uses a schema location to track the incoming schema, and the stream uses a checkpoint so previously processed files are not processed again after a restart.

### Silver

Silver is where I apply the main data-quality rules.

The pipeline:

- converts `event_ts` to a timestamp
- removes records missing the truck ID or event timestamp
- removes NULL coordinates
- validates latitude between -90 and 90
- validates longitude between -180 and 180
- removes duplicate GPS pings

For this dataset I use:

```text
truck_id + event_ts
```

as the deduplication key.

The provided data does not have a unique event ID, and the duplicate records generated by the source have the same truck and event timestamp.

Silver is written using `foreachBatch` and Delta `MERGE`. The MERGE prevents the same ping from being inserted again if it is seen in another batch or the pipeline is rerun.

### Gold

Gold contains the latest known position for each truck.

The Silver GPS stream is joined with the static `truck_details` table to add information such as:

- driver
- make/model
- capacity
- home depot
- region

Within each batch I select the latest event for each truck and MERGE it into `gold_truck_positions`.

An existing truck is only updated when:

```text
incoming event_ts > current event_ts
```

This prevents an older GPS event from replacing a newer position.

The final Gold table therefore contains one current record per truck instead of the complete GPS history.

## Static Reference Data

`truck_details` is read as a static table when the Gold job starts.

Since the pipeline uses `availableNow`, the job finishes after processing the currently available data. The next pipeline run reloads `truck_details`, so changes to the reference data can be picked up on the next run.

One limitation is that changing `truck_details` alone does not update an existing Gold row. A new GPS event for that truck needs to be processed. For a larger production solution I would handle reference-data refresh separately if immediate updates were required.

## Dev / Test / Prod

The project uses one Databricks Asset Bundle with three targets:

| Target | Catalog | Schema |
|---|---|---|
| dev | telematics | dev |
| test | telematics | test |
| prod | telematics | prod |

The same Python code is used in all three environments.

The bundle variables control which schema is used, which also keeps the landing paths, Auto Loader schema locations, and streaming checkpoints separate between environments.

## Running the Project

First confirm that the Databricks CLI is authenticated:

```bash
databricks current-user me
```

Validate the bundle:

```bash
databricks bundle validate -t dev
databricks bundle validate -t test
databricks bundle validate -t prod
```

### Dev

```bash
databricks bundle deploy -t dev
databricks bundle run setup_infrastructure -t dev
databricks bundle run telematics_pipeline -t dev
```

### Test

```bash
databricks bundle deploy -t test
databricks bundle run setup_infrastructure -t test
databricks bundle run telematics_pipeline -t test
```

### Prod

```bash
databricks bundle deploy -t prod
databricks bundle run setup_infrastructure -t prod
databricks bundle run telematics_pipeline -t prod
```

The setup job creates the required schema, volume, tables, truck reference data, and sample GPS files. These objects do not need to be manually created in the workspace.

## Schema Change

I included one versioned schema migration:

```text
001_add_position_updated_at.py
```

The migration adds:

```text
position_updated_at TIMESTAMP
```

to the Gold table.

The migration first checks whether the column already exists before adding it, so it can safely be rerun.

I promoted the change through the same bundle:

```text
dev -> test -> prod
```

For example:

```bash
databricks bundle deploy -t dev
databricks bundle run schema_migrations -t dev
```

The same process is then repeated for test and prod.

This keeps the schema change in source control and avoids manually changing the production table.

## Validation

The `tests/validate_pipeline.sql` file contains the SQL queries I used to validate the pipeline.

The main checks are:

- Bronze receives the raw GPS events
- invalid GPS coordinates do not reach Silver
- duplicate GPS events do not exist in Silver
- Gold contains only one current record per truck
- Gold contains the latest Silver event for each truck
- Gold truck details match the static reference table
- rerunning the pipeline without new files does not create additional records

## Scaling

This implementation is intentionally small for the take-home, but I would keep the same overall Bronze/Silver/Gold design for a larger fleet.

For something closer to 100,000 trucks, I would mainly look at:

- serverless compute sizing
- streaming trigger frequency
- input file sizes
- Delta table layout/clustering
- streaming lag and throughput
- data-quality monitoring

I would also want the source system to provide a unique `event_id` for each GPS ping instead of relying on `truck_id + event_ts` for deduplication.

For production support I would add monitoring around pipeline failures, processing lag, rejected records, throughput, and data-quality metrics.
